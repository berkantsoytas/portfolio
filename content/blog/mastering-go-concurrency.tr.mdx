## Giriş: CSP ve Go Felsefesi

Go'nun concurrency modeli Hoare'in Communicating Sequential Processes (CSP) teorisine dayanır: *belleği paylaşarak iletişim kurma, iletişim kurarak belleği paylaş.* Bu cümleyi ilk okuyuşta kafanda oturmadıysa dert etme — yazının sonunda netleşecek. Concurrency paralellik değildir. Go ikisini de destekler, ama önce concurrency'i doğru kurmanı bekler.

## Goroutine'ler: Süper Hafif Thread'ler

Goroutine'ler OS thread'lerine göre o kadar hafif ki aklın durur. Başlangıç stack'i ~2 KB — OS thread'in ~1-8 MB'ını yanına bile yaklaşamaz. Runtime stack'i ihtiyaca göre otomatik büyütüp daraltır, sen hiç karışmazsın. `go` anahtar kelimesiyle bir fonksiyonu eşzamanlı çalıştırmak tek satır. Binlercesini aynı anda aç, maliyeti neredeyse sıfır.

### M:N Scheduling

GMP modelinde M tane goroutine, N adet OS thread'e dağıtılır. Bu sayede 1:1 (her goroutine = thread) modelinin şişkinliğinden de, N:1 (tümü tek thread) modelinin darboğazından da kurtulursun. İkisinin avantajını alır, derdin ikisini de almazsın.

## GMP Scheduler

Scheduler üç temel yapıdan oluşur. Tanıştırayım:

- **G (Goroutine)**: Çalıştırılacak kod. Stack, instruction pointer, durum bilgisi — hepsi burada.
- **M (Machine)**: OS thread. G'leri alır ve çalıştırır. Makine gibi çalışır yani.
- **P (Processor)**: Scheduling context. G'lerin sıraya dizildiği logical processor. Kaç tane P varsa, aynı anda o kadar iş yapılır.

### Work Stealing

Şöyle düşün: bir P'nin iş kuyruğu boşaldı — ne yapar? Boş boş oturmaz. Diğer P'lerin run queue'sine göz atar, bulursa goroutine çalıp getirir. Buna work stealing denir:

```go
func (pp *p) stealWork() *g {
    for i := 0; i < 4; i++ {
        if g := randomOtherP().runq.pop(); g != nil {
            return g
        }
    }
    return nil
}
```

### Preemption

Go 1.14 öncesi bu iş **cooperative**'di. Yani goroutine'ler canı isterse el değiştirirdi — kanal, syscall ya da fonksiyon çağrısı gibi noktalarda. Ama ya hiçbiri olmazsa? İşte o zaman sorun. Go 1.14'le beraber **asynchronous preemption** geldi. Artık OS sinyalleri (SIGURG) ile goroutine kesilebiliyor, scheduler kontrolü kapıp yola devam ediyor.

### GOMAXPROCS

Logical processor (P) sayısını belirler. Varsayılan değer CPU çekirdek sayısıdır — Go 1.5'ten beri container'larda cgroups'a da saygı duyar. CPU-bound işlerde GOMAXPROCS ile oyna, optimumu yakala.

```go
runtime.GOMAXPROCS(4)
```

## Channel'lar

Tür güvenli, doğrudan, etkili. CSP'nin kalbi diyorum, abartmıyorum.

### Unbuffered vs Buffered

```go
ch := make(chan int)       // senkron: alıcı hazır olana kadar bekler
bufCh := make(chan int, 5) // non-blocking, kapasite dolana kadar
```

Unbuffered channel tam bir senkronizasyon noktası yaratır — gönderen ve alıcı aynı anda hazır olmak zorunda. Buffered ise decoupling ve backpressure sağlar, ikisi arasındaki bağı gevşetir.

### Channel Pattern'leri

**Fan-in / Fan-out:** Çok kaynaktan tek hedefe (fan-in), tek kaynaktan çok işçiye (fan-out). İkisi de iş yükü dağıtmak için klasikleşmiş pattern'lerdir:

```go
func fanIn(chs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, c := range chs {
        wg.Add(1)
        go func(ch <-chan int) {
            defer wg.Done()
            for v := range ch { out <- v }
        }(c)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}
```

**Pipeline:** Veriyi aşama aşama işlersin — her aşama bir kanal alır, bir kanal döndürür. Birleştir gitsin:

```go
gen := func(nums ...int) <-chan int {
    out := make(chan int)
    go func() { for _, n := range nums { out <- n }; close(out) }()
    return out
}
sq := func(in <-chan int) <-chan int {
    out := make(chan int)
    go func() { for n := range in { out <- n * n }; close(out) }()
    return out
}
for n := range sq(gen(1, 2, 3)) { fmt.Println(n) }
```

### Select Multiplexing

Birden çok kanalı tek noktada dinlemek mi istiyorsun? `select` tam da bunun için:

```go
select {
case v := <-ch1: fmt.Println(v)
case <-time.After(100 * time.Millisecond): // timeout
default: // non-blocking
}
```

### Nil Channel'lar

Nil channel'a yazmak da okumak da blokeler. Ama bu bir özellik! Select içinde kolları dinamik olarak devre dışı bırakmak için birebir — fan-in'de tükenen kanalı nil yap, gerisini runtime halletsin.

## Sync Primitive'leri

| Senaryo | Çözüm |
|---|---|
| Veri akışı | Channel |
| State koruma (kısa kilit) | Mutex |
| Çok okuyucu, az yazıcı | RWMutex |
| N işin bitmesi | WaitGroup |
| Tek seferlik init | Once |

```go
type Counter struct {
    mu    sync.Mutex
    value int
}
func (c *Counter) Inc() { c.mu.Lock(); defer c.mu.Unlock(); c.value++ }

var once sync.Once
once.Do(func() { db = connectDB() })
```

## Context Paketi

Cancellation, deadline ve isteğe özgü değerleri API boyunca taşır. Goroutine hayatını yönetmenin resmi yolu budur:

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
select {
case result := <-process(ctx):
case <-ctx.Done():
    return ctx.Err()
}
```

Context alan bir fonksiyon, onu alt çağrılara da iletmek zorunda — yoksa cancellation zinciri kopar, goroutine'ler ortada kalır. `ctx.Done()` pattern'i ile goroutine'ler temiz bir şekilde sonlanır:

```go
go func() {
    for {
        select {
        case job := <-jobCh: process(job)
        case <-ctx.Done(): cleanup(); return
        }
    }
}()
```

## Production Pattern'leri

### errgroup ile Sınırlı Concurrency (golang.org/x/sync)

Bir grup işi paralel çalıştırıp hataları toplamak mı istiyorsun? `errgroup` tam aradığın şey. Üstelik `SetLimit` ile concurrency seviyesini de sınırlarsın:

```go
g, ctx := errgroup.WithContext(context.Background())
g.SetLimit(10)
for _, task := range tasks {
    task := task
    g.Go(func() error { return task.Run(ctx) })
}
if err := g.Wait(); err != nil { log.Fatal(err) }
```

### Rate Limiting

Token bucket mantığı: belirli aralıklarla kovaya token at, işçiler token alabildiği sürece çalışsın. Buffered channel ve `time.Ticker` ile yapması iki satır:

```go
type TokenBucket struct { tokens chan struct{} }
func NewTokenBucket(rate, burst int) *TokenBucket {
    tb := &TokenBucket{make(chan struct{}, burst)}
    go func() {
        ticker := time.NewTicker(time.Second / time.Duration(rate))
        defer ticker.Stop()
        for range ticker.C { select { case tb.tokens <- struct{}{}: default: } }
    }()
    return tb
}
func (tb *TokenBucket) Wait(ctx context.Context) error {
    select { case <-tb.tokens: return nil; case <-ctx.Done(): return ctx.Err() }
}
```

### Graceful Shutdown

Uygulaman kapanırken açık bağlantıları temizlemek zorundasın. `signal.NotifyContext` ile sinyalleri yakala, `Shutdown` ile bekle:

```go
ctx, cancel := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer cancel()
srv := &http.Server{Addr: ":8080"}
go srv.ListenAndServe()
<-ctx.Done()
sdCtx, sdCancel := context.WithTimeout(context.Background(), 30*time.Second)
defer sdCancel()
srv.Shutdown(sdCtx)
```

### Circuit Breaker

Bir state makinesi: kapalıyken hata eşiği aşılınca açılır, timeout sonrası yarı-açık, başarılı olursa tekrar kapanır. `sync.Mutex` ile state korunur. Basit ama dışarı bağımlı her sistemde olmazsa olmaz.

## Debugging

- **Race detector** (`go run -race`): Data race tespiti — development'da çalıştırmasan olmaz, production'a atmadan önce şart.
- **Execution tracer** (`go tool trace`): Goroutine'lerin doğumundan ölümüne her şeyi görürsün. Scheduler olayları, blokelenmeler, hepsi burada.
- **pprof** (`net/http/pprof`): Goroutine leak, mutex contention, CPU profiling — üretimde can kurtaran.

## Yaygın Hatalar

**Goroutine leak:** Açtığın goroutine bir şekilde sonlanmaz ve arkanda ölü işlem olarak kalır. Context veya kanal kapatma ile çözülür:

```go
// KÖTÜ
go func() { <-ch }() // sonsuz bekler
// İYİ
go func() { select { case <-ctx.Done(): return; case v := <-ch: use(v) } }()
```

**sync.Mutex kopyalamak:** Değer alıcılı bir metot yazarsan Mutex'i kopyalarsın — ve koruma diye bir şey kalmaz. Pointer receiver kullan, kopyalama olmasın.

**WaitGroup.Add'i goroutine içinde:** `Add`'i goroutine dışında çağırmazsan race condition doğar. Önce `Add`, sonra `go`:

```go
// KÖTÜ: go func() { wg.Add(1); task.Run(); wg.Done() }()
// İYİ: wg.Add(1); go func() { defer wg.Done(); task.Run() }()
```

**time.Sleep ile senkronizasyon:** "5 saniye bekle, iş bitmiştir" mantığı garantisizdir. Yarış şartlarını Sleep'le çözmeye çalışanı döverler. Kanal veya WaitGroup kullan:

```go
go func() { done <- true }()
<-done // garantili
```

## Özet

| Konu | İlke |
|---|---|
| Goroutine lifecycle | Açtığını kapat — context/kanal ile sonlandır |
| Channel ownership | Gönderen kapatır, alıcı kapatamaz |
| Mutex vs Channel | Data flow → channel, state protection → mutex |
| Error handling | errgroup ile concurrency + hata yönetimi |
| Debugging | `-race` zorunlu, production'da pprof + trace |

Go'nun concurrency modeli basit görünür ama derine indikçe derinleşir. Aklında şu kalsın: her goroutine'in bir sorumluluğu, her kanalın bir yönü ve bir sahibi olsun.
