## Neden Event-Driven?

Blokzincir verisi doğası gereği event-driven'dır. Her blok, her transaction bir event'tir. Geleneksel polling yaklaşımı yerine event-driven mimari kullanmak:

- **Gerçek zamanlı** — Yeni bloklar gelir gelmez işlenir
- **Ölçeklenebilir** — Consumer'lar bağımsız scale edilebilir
- **Esnek** — Yeni consumer eklemek mevcut sistemi etkilemez

## Mimari

### Kafka Topic Tasarımı

```
raw-blocks          → Ham blok verileri (partitioned by block number)
parsed-transactions → Ayrıştırılmış transaction'lar
events              → İşlenmiş event'ler (transfer, swap, vs.)
alerts              → Anomali ve uyarılar
```

### Producer — Blok Dinleyici

```typescript
class BlockListener {
    private producer: KafkaProducer;

    async listen() {
        for await (const block of this.steemNode.streamBlocks()) {
            await this.producer.send({
                topic: "raw-blocks",
                key: block.number.toString(),
                value: JSON.stringify(block),
            });

            for (const tx of block.transactions) {
                await this.producer.send({
                    topic: "parsed-transactions",
                    key: tx.id,
                    value: this.parseTransaction(tx),
                });
            }
        }
    }
}
```

### Consumer — İşlem Hattı

```typescript
class TransactionProcessor {
    async consume() {
        const consumer = this.kafka.consumer({ groupId: "tx-processor" });
        await consumer.subscribe({ topic: "parsed-transactions" });

        await consumer.run({
            eachMessage: async ({ message }) => {
                const tx = JSON.parse(message.value!.toString());
                const events = this.extractEvents(tx);

                for (const event of events) {
                    await this.producer.send({
                        topic: "events",
                        key: event.id,
                        value: JSON.stringify(event),
                    });
                }
            },
        });
    }
}
```

### Dead Letter Queue

İşlenemeyen mesajlar için DLQ (Dead Letter Queue) zorunludur:

```typescript
try {
    await processTransaction(tx);
} catch (err) {
    await producer.send({
        topic: "dead-letter-queue",
        key: tx.id,
        value: JSON.stringify({ tx, error: err.message, retryCount }),
    });
}
```

## Partition Stratejisi

Blok numarasına göre partitioning, sıralı işleme garantisi verir:

- Block N her zaman aynı partition'a gider
- Consumer'lar block sırasını koruyarak işler
- Partition sayısı kadar parallel consumer çalışabilir

## Çıkarılan Dersler

1. **Offset management kritik** — Consumer crash'ten sonra kaldığı yerden devam edebilmeli
2. **Idempotency şart** — Aynı mesaj iki kez işlenirse bile sonuç aynı olmalı
3. **Schema evolution** — Avro veya Protobuf ile schema registry kullan
4. **Monitoring** — Consumer lag, throughput, error rate sürekli izlenmeli
