## Giriş

Rust'ın tip sistemi, diğer dillerde runtime'da kontrol etmek zorunda olduğun şeyleri daha derleme aşamasında garanti eder. Null pointer, use-after-free, data race — hepsi tip seviyesinde elenir. İşin güzel tarafı, bunların hiçbiri runtime overhead getirmez. Üç temel prensip:

**Zero-cost abstractions**: Bir soyutlama kullanıyorsan, sanki hiç kullanmamışsın gibi performans alırsın. Iterator chain'ler, closure'lar, generic'ler — hepsi elle yazdığın en iyi koda birebir derlenir.

**Compile-time guarantees**: Ownership, lifetime, thread-safety, state machine geçişleri — aklına ne gelirse derleme anında kontrol edilir. Runtime'da sürpriz yok.

**Expression-driven types**: `if`, `match`, `loop` — bunların hepsi bir değer üretir. Yani her şeyin bir tipi vardır, boşluk yok.

## Traits

Trait'ler Rust'ın interface'leridir. OOP'deki gibi kalıtım yok; composition var, delegation var.

```rust
trait Area { fn area(&self) -> f64; }

struct Circle { radius: f64 }
struct Triangle { base: f64, height: f64 }

impl Area for Circle {
    fn area(&self) -> f64 { std::f64::consts::PI * self.radius * self.radius }
}
impl Area for Triangle {
    fn area(&self) -> f64 { 0.5 * self.base * self.height }
}
```

Orphan rule: eğer bir trait'i ya da tipi sen tanımlamadıysan, o trait'i o tip için implemente edemezsin. Bu kural coherence'ı (tutarlılığı) garanti eder — aynı implementasyonun birden fazla yerde çakışmasını engeller.

### Trait Bound'lar ve Where Clauses

```rust
fn print_area<T: Area>(shape: &T) { ... }

fn print_areas<T, U>(a: &T, b: &U)
where
    T: Area + Debug,
    U: Area + Display,
{ ... }
```

Where clauses kodu daha okunabilir yapar, özellikle birden çok bound olduğunda. Ayrıca associated type'ları bound'lama gibi ileri düzey kullanımlara da izin verir.

### Derive, Default ve Supertrait'ler

`#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]` ile sık kullanılan trait'leri otomatik türetebilirsin. Her derive'ın kendi kuralları var: `Copy` için tüm alanlar `Copy` olmalı, `Eq` reflexivity garantisi ekler.

Trait'ler varsayılan metod implementasyonu da içerebilir. Bu sayede bir trait'e sonradan yeni metot eklemek backward-compatible olur — mevcut implementasyonlar bozulmaz.

Bir trait başka bir trait'i genişletebilir (supertrait):

```rust
trait Drawable { fn draw(&self); }
trait Clickable: Drawable { fn click(&self); }
```

`Clickable`'ı, `Drawable`'ı da implemente etmiş tiplerde kullanabilirsin.

## Generics ve Monomorphization

```rust
struct Container<T> { value: T }
fn id<T>(x: T) -> T { x }
```

Rust generic'leri monomorphize eder: her bir tip kombinasyonu için ayrı bir kod kopyası üretilir.

```rust
let a = id(42);    // __id_i32
let b = id(3.14);  // __id_f64
```

**Zero-cost**: vtable yok, dynamic dispatch yok, hiçbir runtime overhead yok. **Maliyeti**: code bloat — 50 farklı tip için 50 ayrı kopya derlenir. Kritik sistemlerde binary boyutunu kontrol altında tutmak gerekir.

### impl Trait vs Generics

Parametre pozisyonunda ikisi arasında fark yok — ikisi de monomorphize edilir. Ama dönüş pozisyonunda iş değişir. `impl Trait` döndüğünde gerçek tip gizlenir (existential type) ama yine de tek bir somut tip döndürebilirsin. Farklı koşullarda farklı tipler döndürmen gerekiyorsa `Box<dyn Trait>` gerekir.

### Const Generics (1.51+)

```rust
struct Array<T, const N: usize> { data: [T; N] }
```

Compile-time'da bilinen herhangi bir boyut. Dizi, matris, buffer gibi yapılarda tip güvenliği sağlar.

## Trait Object'leri

| Yaklaşım | Dispatch | Boyut |
|---|---|---|
| `fn<T: Trait>(t: T)` | Static (monomorphization) | Büyük binary |
| `fn(t: &dyn Trait)` | Dynamic (vtable) | Tek pointer + vtable |
| `fn(t: &impl Trait)` | Static | Generic ile aynı |

dyn Trait heterojen koleksiyonlar için biçilmiş kaftan:

```rust
let shapes: Vec<Box<dyn Area>> = vec![
    Box::new(Circle { radius: 1.0 }),
    Box::new(Triangle { base: 3.0, height: 4.0 }),
];
```

**Object safety**: her trait dyn olarak kullanılamaz. Dönüş tipi `Self` olan, generic parametre alan veya `Sized` bound'ı olmayan trait'ler object-safe değildir.

**Vtable overhead**: pointer → vtable → fonksiyon şeklinde iki kere indirection var. Üstelik inline da edilemez. O yüzden sıcak döngülerde generics kullanmak daha iyidir.

## Associated Types vs Generics

```rust
trait Iterator {
    type Item;                          // her tip için tek bir Item
    fn next(&mut self) -> Option<Self::Item>;
}

trait Convert<To> {                      // aynı tip, farklı dönüşümler
    fn convert(&self) -> To;
}
```

Karar kuralı basit: trait'in bir tip için tek bir doğal implementasyonu varsa associated type kullan. Ama aynı tipin birden fazla varyasyonu olacaksa — mesela bir tipten birden çok farklı dönüşüm — o zaman generic parametre.

## Marker Traits

Hiç metodu olmayan, sadece type-level bilgi taşıyan trait'ler. Derleyiciye bir şeylerin garantisini verirsin, başka bir şey yapmaz.

### Send ve Sync

```rust
unsafe auto trait Send { }
unsafe auto trait Sync { }
```

- `Send`: ownership thread'ler arasında transfer edilebilir
- `Sync`: `&T` birden fazla thread'de kullanılabilir

`Rc<T>`: Send veya Sync değildir (non-atomic refcount). `Arc<T>` ve `Mutex<T>`: Send + Sync. Thread-safety hataları daha runtime'da patlamadan compile-time'da yakalanır.

### Sized, Copy, Clone

Varsayılan olarak her generic `Sized` kabul edilir. `?Sized` DST'ler (dynamically sized types) içindir: `[u8]`, `dyn Trait`, `str`. Generic parametrelere implicit olarak `Sized` bound'ı eklenir — istisna istiyorsan `?Sized` ile açıkça belirtmen gerekir.

`Clone`: heap tahsisi yapabilir, açıkça `.clone()` çağırmak gerekir. `Copy`: bitwise kopya, implicit. `Drop` ile `Copy` aynı anda var olamaz — bir şeyin destructor'ı varsa kopyalanması mantıklı değildir.

### PhantomData

Tip sistemine "bu tip kullanılmıyor gibi görünüyor ama aslında bir bağımlılık var" demek için kullanılır:

```rust
struct ForeignKey<T> {
    id: u64,
    _marker: PhantomData<T>,
}
```

`PhantomData<T>` drop checker'a "bu yapı aslında T'ye sahipmiş gibi davran" der. Lifetime ve drop analizi buna göre yapılır. Runtime'da hiçbir karşılığı yoktur, sadece compile-time'da var olur.

## Zero-Cost Abstractions

```rust
let sum: i32 = (0..100)
    .filter(|x| x % 2 == 0)
    .map(|x| x * x)
    .sum();
```

Bu kod derlenince iterator chain tek bir döngü haline gelir. Closure'lar inline edilir, ara tahsisler yok olur. Elle yazılmış bir `for` döngüsüyle aynı assembly üretilir.

`Option<T>` ve `Result<T, E>` da sıfır runtime overhead ile çalışır. Niche optimization sayesinde `Option<NonNull<T>>` tek pointer boyutuna iner. Closure'lar da `Box<dyn Fn()>` ile sarmalamadığın sürece heap tahsisi yapmaz.

## Advanced Pattern'ler

### Type-State Pattern

State'leri tiplerle kodlayarak geçersiz durumları compile-time'da elersin:

```rust
struct Closed;
struct Open;
struct Door<State = Closed> { _state: PhantomData<State> }

impl Door<Closed> { fn open(self) -> Door<Open> { ... } }
impl Door<Open>   { fn close(self) -> Door<Closed> { ... } }
```

`Door<Closed>` iken `close()` çağırmak derleme hatası verir. Çünkü kapalı bir kapıyı kapatamazsın — bu runtime'da değil, compile-time'da patlar.

### Newtype Pattern

```rust
struct UserId(u64);
struct OrderId(u64);

get_user(OrderId(42));   // derlenmez
get_user(UserId(42));    // derlenir
```

Sıfır runtime overhead. Tek derdi: içteki tipe `.0` ile erişmen gerekir, biraz göz yorar.

### PhantomData ile Type-Level State

```rust
struct Protocol<State> { buffer: Vec<u8>, _state: PhantomData<State> }
struct AwaitingHandshake;
struct Authenticated;
struct Ready;

impl Protocol<AwaitingHandshake> { fn handshake(self) -> Result<Protocol<Authenticated>, Error> { ... } }
impl Protocol<Authenticated>     { fn prepare(self) -> Protocol<Ready> { ... } }
impl Protocol<Ready>             { fn send(&self, data: &[u8]) { ... } }
```

Yanlış sırada mesaj göndermeye kalkarsan derlenmez. Protocol'ün hangi aşamada olduğu tip tarafından belirlenir.

### Builder + Type-State

Zorunlu alanları compile-time'da kontrol etmek için birebir:

```rust
struct RequestBuilder<HasUrl, HasMethod> { ... }
struct Yes;
struct No;

impl RequestBuilder<No, No> {
    fn new() -> Self { ... }
    fn with_url(self, url: &str) -> RequestBuilder<Yes, No> { ... }
    fn with_method(self, method: &str) -> RequestBuilder<No, Yes> { ... }
}
impl RequestBuilder<Yes, Yes> { fn build(self) -> Request { ... } }
```

Runtime'da `unwrap()` ile uğraştıran kontrolleri compile-time'a taşır. URL verilmeden `build()` çağrılamaz — derleyici izin vermez.

### Sealed Traits

Trait'in sadece aynı crate içinde implemente edilmesini sağlamak:

```rust
mod internal { pub trait Sealed {} }

pub trait PublicTrait: internal::Sealed { fn method(&self); }
```

Dışarıdaki crate'ler bu trait'i kullanabilir ama implemente edemez. Implementasyon seti kapalı kalır, böylece trait'e yeni metot eklemek güvenli olur.

## Sonuç

Rust'ın tip sistemi, programcının niyetini compile-time'da ifade etmesini sağlar. Trait'ler ve generic'ler davranışı soyutlar, associated type'lar modeli doğal tutar, marker trait'ler thread-safety ve layout'u type-level'a taşır.

Type-state, newtype ve sealed traits teknikleriyle sadece "doğru tipte" değil, "doğru durumda" kod yazılır. Hatalar runtime'da patlamaz, compile-time'da kalır. Zero-cost abstraction sayesinde bütün bu güvenceler performanstan ödün vermez.

Rust'ın tip sistemini anlamak, onu memory-safe C alternatifi olmaktan çıkarıp **compile-time doğruluk kanıtlayıcısı** olarak kullanmaktır. Her `impl`, her generic, her marker — compiler'a "bu program şu invariant'ları sağlar" diye kanıt sunmaktır.
