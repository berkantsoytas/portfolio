## Giriş: "Derleyici Neden Hayatımı Zorlaştırıyor?"

Rust'a Java veya Go tarafından geliyorsanız, derleyiciyle ilk tanıştığınızda hissettiğiniz şey tam olarak bu. GC sizi elle bellek yönetimi derdinden kurtarır ama runtime maliyeti vardır. C/C++ size tam kontrol verir, ama bedeli ağırdır — `use-after-free`, dangling pointer, segfault'larla elle uğraşmak zorunda kalırsınız.

Rust üçüncü bir yol sunar: **compile-time memory safety**. Ne GC vardır ne de manuel `free`. Derleyici, program daha çalışmadan bellek güvenliğini garanti eder. Bunu sağlayan mekanizmanın adı **ownership**. Bu yazıda ownership'in sadece bir kural seti olmadığını, sistem tasarımınızı baştan sona değiştiren bir zihinsel model olduğunu göstereceğim.

## Ownership Kuralları

Üç basit kural, hepsi bu: (1) her değerin tam olarak bir sahibi (owner) vardır, (2) owner scope'tan çıkınca değer otomatik olarak drop edilir, (3) bir değerin aynı anda birden fazla sahibi olamaz.

### Move Semantics Varsayılandır

```rust
let s1 = String::from("hello");
let s2 = s1;                    // move: s1 artık geçersiz
// println!("{}", s1);          // ❌ compile error
```

`String` gibi heap'te yaşayan tiplerde atama yapmak **move** anlamına gelir. Shallow copy yapılır, ama eski sahibi geçersiz hale gelir — yani aynı bellek bölgesini iki pointer göstermez. Bu sayede double free hatası compile-time'da yakalanır. Stack-only tipler (`i32`, `bool`) ise `Copy` trait'i sayesinde otomatik kopyalanır, move olmaz.

### Clone vs Copy

`Copy` bitwise kopya yapar ve sıfır runtime maliyeti vardır. Ama yalnızca `Drop` implemente etmeyen tiplerde çalışır — mantık basit: özel bir cleanup kodunuz varsa, otomatik bitwise kopya güvenli değildir. `Clone` ise explicit bir derin kopyadır, heap allocasyonu gerektirir:

```rust
let s1 = String::from("hello");
let s2 = s1.clone();            // heap kopyalanır
println!("{}", s1);             // ✅
```

Kural: tipiniz `Clone` ise `Copy` de olabilir mi diye kendinize sorun. Cevap hayırsa, her kopyalama ya maliyetlidir ya da tamamen yasaktır.

### Fonksiyon Çağrılarında Move

```rust
fn take(s: String) { /* drop */ }
let s = String::from("merhaba");
take(s);
// println!("{}", s);           // ❌ ownership taşındı
```

Fonksiyon çağrıları da aynı şekilde move demektir. Parametreye verdiğiniz değerin sahipliği hemen fonksiyona geçer. Ownership'i geri almanın iki yolu var: ya return edersiniz ya da borrowing kullanırsınız.

## Borrowing

Her şeyi move etmek zorunda kalsaydık fonksiyon yazmak işkence olurdu. Neyse ki reference'lar (`&T` / `&mut T`) var: veriyi ödünç alırsınız, sahipliği devretmezsiniz. Borrowing denen şey tam olarak bu.

### Çok Okuyucu XOR Bir Yazıcı

Rust'ın en kritik borrowing kuralı şudur: **birden fazla `&T` olabilir VEYA bir tane `&mut T` olabilir, ikisi aynı anda olamaz:**

```rust
let mut s = String::from("hello");
let r1 = &s;
let r2 = &s;                    // ✅ çok okuyucu
// let r3 = &mut s;             // ❌ — zaten immutable borrow var
println!("{} {}", r1, r2);      // kullanım bitene kadar
let r3 = &mut s;                // ✅ — eski borrow'lar bitti
r3.push_str("!");
```

Bu kural data race'lerin runtime'a çıkmasını daha baştan engeller. Bir tane yazıcı varsa, o anda kimse okuyamaz. Basit ama etkili.

### NLL (Non-Lexical Lifetimes)

Rust 2018'den önce borrow'lar içinde bulundukları scope'un sonuna kadar yaşardı. NLL (Non-Lexical Lifetimes) ile birlikte borrow'lar son kullanıldıkları noktada biter — daha esnek, daha akıllı:

```rust
let mut s = String::from("hello");
let r = &s;
println!("{}", r);              // r son kullanım
let r2 = &mut s;                // ✅ NLL sayesinde
```

### Dangling Reference'ların Önlenmesi

```rust
fn dangling() -> &String {
    let s = String::from("hello");
    &s                          // ❌ s drop olur, reference dangling
}
```

Derleyici şunu garanti eder: bir reference, gösterdiği değerden daha uzun yaşayamaz. C/C++'ta runtime'da patlamaya neden olan bug'lar compile-time'da yakalanır — segfault yok, core dump yok.

## Lifetime'lar

Lifetime annotation'ları (`'a`, `'b`) reference'lar arasındaki **yaşam süresi ilişkisini** belirtir. Runtime'da hiçbir şey değişmez — sadece borrow checker'ın işini kolaylaştıran etiketlerdir.

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Anlamı: `x` ve `y` en az `'a` kadar yaşamalı, dönüş değeri de en fazla `'a` kadar yaşayabilir. Lifetime'lar input ve output arasında bir **ilişki** kurar, hepsi bu.

### Elision Kuralları

Her fonksiyona lifetime annotation'ı yazmak zorunda değilsiniz — derleyici sizin yerinize düşünür. Elision kuralları dediğimiz şu üç kuralı otomatik olarak uygular: (1) her input reference kendi lifetime'ını alır, (2) tek bir input reference varsa output onun lifetime'ını alır, (3) `&self` varsa output `self`'in lifetime'ını alır.

```rust
fn first_word(s: &str) -> &str { /* elision yeterli */ }
```

Lifetime'ları elle yazmanız gereken durumlar genelde şunlar: birden fazla input reference varsa ve output döndürüyorsanız, ya da struct method'larında farklı lifetime'ları birbirinden ayırmanız gerekiyorsa.

### 'static ve Struct Lifetime

`'static`, programın tamamı boyunca geçerli olan reference'lar içindir. String literal'leri `'static`'dir. Bir struct reference tutuyorsa lifetime parametresi bildirmek zorundasınız — derleyici bunu ister:

```rust
struct Parser<'a> { input: &'a str }
impl<'a> Parser<'a> {
    fn parse(&self) -> &'a str { &self.input[..5] }
}
```

## Interior Mutability

Normalde `&T` üzerinden veriyi değiştiremezsiniz — kural kuraldır. Ama bazen immutable bir reference üzerinden mutasyon yapmanız gerekir (cache'leme, reference counting gibi durumlarda). **Interior mutability** pattern'leri tam olarak bu ihtiyacı karşılar.

| Mekanizma | Check Zamanı | Thread-safe | Maliyet |
|-----------|-------------|-------------|---------|
| `&T` / `&mut T` | Compile-time | Evet | Sıfır |
| `Cell<T>` | Compile-time | Hayır | Sıfır (Copy için) |
| `RefCell<T>` | Runtime | Hayır | Borrow count |
| `Mutex<T>` | Runtime | Evet | Lock contention |
| `RwLock<T>` | Runtime | Evet | Read-biased lock |

`Cell<T>` yalnızca `Copy` tipler için çalışır, `set()`/`get()` ile sıfır maliyetlidir. `RefCell<T>` borrow kurallarını runtime'a taşır — ihlal panic atar. `Mutex` ve `RwLock` thread-safe varyantlardır.

Altın kural: önce compile-time guarantee'leri kullanın, runtime çözümlere ancak gerçekten ihtiyacınız varsa geçin.

## Smart Pointer'lar

### Box, Rc, Arc

```rust
let b = Box::new(42);                   // heap, tek sahip
let r = Rc::new("merhaba".to_string()); // referans sayacı, tek thread
let a = Arc::new(vec![1, 2, 3]);        // atomic RC, çok thread
```

`Box<T>` özellikle recursive type'lar ve trait object'ler için biçilmiş kaftandır — boyutu compile-time'da bilinemeyen tipleri heap'e koyar. `Rc<T>` ile paylaşılan ownership mümkün olur (tek thread içinde). `Arc<T>` ise atomic sayaç kullanarak thread-safe hale gelir.

### RefCell + Rc/Arc

```rust
let shared = Rc::new(RefCell::new(42));
let r1 = Rc::clone(&shared);
let r2 = Rc::clone(&shared);
*r1.borrow_mut() += 1;
```

Bu kombinasyon paylaşılan mutable state'i mümkün kılar, ama bedeli vardır: borrow checking runtime'a taşınır ve hata yaparsanız panic yersiniz. Dikkatli kullanın.

## Yaygın Pattern'ler

**Builder + Ownership Chain**: Her method `self` alır ve `Self` döndürür. Partial state'ler compile-time'da garanti altındadır.

**Type-State Pattern**: Her state geçişi farklı bir type ile temsil edilir. Geçersiz bir geçiş yapmaya kalkarsanız compile-time hatası alırsınız — runtime'da patlamak yok, panic yok:

```rust
struct Connection<State> { _state: State }
impl Connection<Empty> { fn connect(self) -> Connection<Waiting> { /* ... */ } }
impl Connection<Ready> { fn send(&self, data: &[u8]) { /* ... */ } }
// Connection<Empty> üzerinde send() çağırmak ❌ compile error
```

**Arena Allocation**: Cyclic reference'lardan kaçınmanın en temiz yolu referans yerine indeks kullanmaktır. Tüm nesneler bir vektörde toplanır, ownership tektir, borrow checker mutlu.

**Typed ID**: Reference yerine `EntityId(u64)` gibi bir ID tutarsanız lifetime dertlerinden kurtulursunuz. Oyun motorlarında ve ECS sistemlerinde çok yaygındır.

## Tuzaklar ve Çözümleri

**Self-referential struct'lar**: Rust'ın sevmediği şeylerin başında gelir. Struct taşındığında iç pointer geçersiz kalır. `Pin<T>` taşınmayı engelleyerek bu sorunu çözer, genelde async/future implementasyonlarında kullanılır.

**Fazla lifetime annotation**: Elision yeterliyse annotation eklemeyin. Derleyici sizden daha akıllıdır, gereksiz yere işini zorlaştırmayın. Ama hata alırsanız, anlamak için annotation ekleyip derleyiciye "ne istiyorsun" diye sorun.

**Closure capture**: Closure'lar çevrelerindeki değişkenleri yakalarken borrow checker'ı zorlayabilir. Çözüm basit: closure'ı bir scope içinde kullanıp borrow'ı erken bitirin, ya da `move` ile ownership'ı closure'a devredin.

**Nested borrow + NLL sınırlamaları**: Birden fazla method çağrısında borrow path takibi bazen yetersiz kalabilir. Çözüm: scope'ları iyi ayırmak ya da indeks bazlı erişime geçmek.

## Özet

| Kavram | Ne İşe Yarar | Maliyeti |
|--------|-------------|----------|
| Ownership | Bellek güvenliği (GC yok, manuel free yok) | Compile-time |
| Move | Tek sahip, double-free yok | Sıfır runtime |
| Borrow (&T / &mut T) | Data race prevention | Sıfır (compile-time) |
| Lifetime | Dangling reference önleme | Sıfır (compile-time) |
| RefCell | Runtime borrow checking | Runtime borrow count |
| Rc/Arc | Paylaşılan ownership | Counter (atomic/non-atomic) |
| Pin | Self-referential safety | Sıfır (API restriction) |

Rust'ın ownership modeli bir kısıtlama değil, bir **özgürlük aracıdır**. GC'nin runtime maliyetini ödemeden, C/C++'ın undefined behavior riskini almadan bellek güvenliği istiyorsanız bu modeli benimsemek zorundasınız. Sistem tasarımınızı baştan ownership-aware tasarlayın, derleyici size teşekkür edecek — en güzel teşekkürü de sessiz kalarak yapacak.
